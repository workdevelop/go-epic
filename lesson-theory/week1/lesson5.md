# 📔 Теоретична частина. День 5: інтерфейси та качине типування (duck typing)

Сьогодні ваша команда пройде через один із найзахопливіших ментальних зсувів у Go. Ми повністю закриємо питання поліморфізму та заміни класичного ООП.

У PHP інтерфейси є потужним інструментом для розв'язання архітектурних задач та побудови чистих абстракцій. Проте підхід Go до інтерфейсів докорінно змінює правила гри: тут немає ключового слова `implements`, а сумісність типів визначається виключно їхньою фактичною поведінкою.

## 🧠 Неявні інтерфейси: що таке "качине типування"

В PHP, якщо ви хочете, щоб клас відповідав інтерфейсу, ви зобов'язані прописати це в коді явно:

```php
interface UnitInterface {
    public function move();
}

class Mage implements UnitInterface {
    public function move() { ... }
}
```

Якщо ви забудете написати `implements`, PHP видасть помилку типу (`TypeError`), навіть якщо всередині класу є ідеально написаний метод `move()`.

В Go діє принцип неявного (імпліцитного) інтерфейсу, який часто описують правилом качиного типування:

> «Якщо щось ходить як качка, плаває як качка і крякає як качка — то це, скоріш за все, і є качка».

Якщо ви оголошуєте інтерфейс `Unit` із методом `Move()`, а ваша структура `Mage` має метод `Move()`, то `Mage` автоматично і неявно реалізує цей інтерфейс. Розробнику структури навіть не потрібно знати про існування цього інтерфейсу!

```go
package models

// Оголошуємо інтерфейс
type Unit interface {
    Move(dx, dy int)
    IsAlive() bool
}
```

Щойно компілятор бачить, що у `Mage` та `Orc` є точні реалізації методів `Move(int, int)` та `IsAlive() bool`, він дозволяє приводити ці структури до типу `Unit`.

## 🏗️ Поліморфізм у Mage Arena: один зріз для всієї армії

До сьогоднішнього дня наш `World` мав два окремі зрізи: `Mages []Mage` та `Orcs []Orc`. Коли ми хотіли змусити всіх зробити хід, нам доводилося писати два майже ідентичні цикли `for` — спочатку для магів, потім для орків. Це порушує принцип DRY (Don't Repeat Yourself).

Завдяки інтерфейсам ми можемо кардинально покращити архітектуру. Ми об'єднаємо всіх персонажів в один універсальний зріз інтерфейсів:

```go
type World struct {
    Width  int
    Height int
    Units  []Unit // Тут можуть лежати і Маги, і Орки, і майбутні Дракони чи Зомбі
}
```

Тепер наш метод `Tick()` перетворюється на елегантний та лаконічний цикл:

```go
func (w *World) Tick() {
    for i := 0; i < len(w.Units); i++ {
        if w.Units[i].IsAlive() {
            w.Units[i].Move(1, 0) // Кожен юніт ходить за своєю власною логікою!
        }
    }
}
```

## ⚙️ Зсув мислення: справжня інкапсуляція та "порожній інтерфейс"

Для PHP-розробників важливо зрозуміти два правила екосистеми Go:

- Інтерфейси мають бути крихітними. В PHP ми часто створюємо великі інтерфейси (наприклад, `RepositoryInterface` з 10 методами для CRUD). В Go золотим стандартом є інтерфейси з 1–2 методами (наприклад, `Reader`, `Writer`). Маленькі інтерфейси легше перевикористовувати та комбінувати через композицію.
- Що таке `interface{}` (або `any`): якщо інтерфейс не має жодного методу, йому відповідає абсолютно будь-який тип даних у Go (число, рядок, будь-яка структура). Це аналог типу `mixed` у PHP. Проте не зловживайте ним: Go — мова зі строгою типізацією, і приховування типів за `any` позбавляє вас захисту компілятора.

## 🎯 Що ми робимо на практиці в п'ятницю?

- Кожен розробник створює свою гілку за шаблоном `feature/{name}-day-5`.
- В окремому файлі `internal/models/unit.go` створюємо інтерфейс `Unit` із методами `Move(dx, dy int)` та `IsAlive() bool`.
- Оновлюємо структуру `World`: замість окремих полів `Mages` та `Orcs` залишаємо одне спільне поле `Units []Unit`.
- Переписуємо логіку рендерингу карти в `main.go`. Тепер ми проходимо по одному єдиному списку `Units`. Щоб зрозуміти, яку літеру малювати (`M` чи `O`), ми застосуємо механізм перевірки типів Go — `type assertion` або `type switch` (аналог `instanceof` в PHP).
- Запускаємо гру і переконуємося, що поліморфний код працює значно чистіше, а додавання нових типів істотно спростилося.
