# 📔 Теоретична частина. День 3: методи структур і заміна ООП-класів

У перші два дні ми працювали в процедурному стилі: створювали структури з даними в одному пакеті, а функції для їхньої зміни — в іншому. Для PHP-розробників, звиклих до інкапсуляції всередині класів, такий розподіл коду може виглядати незвично.

Сьогодні ми розберемо, як Go вирішує цю задачу. В Go немає ключового слова `class`, але є методи структур, які дозволяють об'єднати дані та поведінку в одну логічну сутність.

## 🧠 Анатомія методу в Go: що таке ресивер (receiver)

В PHP метод класу автоматично має доступ до внутрішніх властивостей через приховану змінну `$this`.

В Go все робиться абсолютно явно за допомогою ресивера (отримувача). Ресивер — це додатковий аргумент, який описується у круглих дужках перед назвою функції. Він буквально "прив'язує" цю функцію до конкретного типу даних.

Поглянемо на синтаксис ідіоматичного методу руху для нашого Орка:

```go
package models

//          ┌── Ресивер (аналог $this в PHP)
//          │       ┌── Ім'я методу
//          ▼       ▼
func (o *Orc) Move(dx int, dy int) {
    o.X += dx // Змінюємо дані всередині Орка
    o.Y += dy
}
```

Коли ми оголосили таку функцію, Go дозволяє нам викликати її через крапку, точно так само, як стрілочку `->` в PHP:

```go
orc := models.Orc{...}
orc.Move(1, -1) // Виклик методу
```

## 🔑 Два типи ресиверів: за значенням vs за вказівником

Оскільки в Go діє залізне правило "усе копіюється, якщо не вказано інше", ресивери методів діляться на два типи. Це найважливіша концепція дня для вашої команди.

### 1. Ресивер-вказівник (`o *Orc`) — мутатори (сеттери)

Якщо методу потрібно змінити стан об'єкта (координати, здоров'я, ману), ресивер обов'язково повинен бути вказівником (`*`).

Як працює: Go не копіює структуру, а передає в метод її адресу. Усі зміни всередині методу відобразяться на оригінальному юніті у нашому світі `World`.

### 2. Ресивер-значення (`o Orc`) — інспектори (геттери)

Якщо метод використовується лише для читання даних (наприклад, розрахувати відстань, перевірити чи живий юніт, згенерувати текстовий лог) і не змінює властивостей, ресивер описується як звичайне значення без зірочки.

Як працює: Go робить повну локальну копію структури для цього методу. Навіть якщо ви випадково зміните там якесь поле, оригінал залишиться в безпеці. Це захищає від небажаних побічних ефектів (side-effects).

## ⚙️ Зсув мислення: повна відмова від наслідування (inheritance)

У PHP бекенді наслідування є базовим інструментом:

```php
class Unit {
    public int $hp;
}

class Orc extends Unit {
    public int $damage;
}
```

В Go наслідування не існує взагалі. Ви не можете розширити структуру іншої структури. Замість цього Go пропагує принцип "Composition over Inheritance".

Ви вже застосували цей принцип у перший день, коли вбудували `Position` всередину `Mage` та `Orc`. Сьогодні ви побачите магію цього підходу: якщо структура `Position` матиме свій метод, наприклад `IsAt(x, y int) bool`, то завдяки анонімному вбудуванню цей метод автоматично з'явиться і в `Mage`, і в `Orc`.

## 🎯 Що ми робимо на практиці в середу?

- Кожен розробник створює персональну гілку `feature/{name}-day-3`.
- Повністю прибираємо файл `internal/engine/movement.go` (процедурний стиль нам більше не потрібен).
- Переносимо логіку всередину пакету `internal/models/`.
- Для моделей `Mage` та `Orc` реалізуємо:
  - метод руху з ресивером-вказівником: `Move(dx, dy int)`;
  - метод отримання шкоди з ресивером-вказівником: `TakeDamage(amount int)`;
  - метод перевірки стану з ресивером-значенням: `IsAlive() bool`, який повертає `true`, якщо `Health > 0`.
- У файлі `main.go` імітуємо першу міні-дуель: маг та орк роблять кроки назустріч один одному за допомогою нових методів, після чого орк б'є мага, викликаючи метод `TakeDamage()`.
