# 📔 Теоретична частина. Тиждень 3, День 5 (День 17): Оператор select та неблокуюче керування каналами

У попередній день (Четвер) ми перевели нашу гру на подієво-орієнтовану модель (Event-Driven). Юніти більше не чіпають пам'ять світу напрямую, а надсилають повідомлення в канал подій, які ми вичитуємо в головному потоці. Проте виникла архітектурна дилема: читання з каналу є блокуючою операцією. Якщо в каналі немає подій, головний потік зависає на рядку `<-channel` і чекає. Через це наш фоновий таймер рендерингу (`time.Ticker`) починає відставати, а кадр гри не оновлюється вчасно.

Сьогодні ми вивчимо інструмент, який вирішує цю проблему і є унікальним для мови Go — **оператор `select`**. Ми навчимо головний цикл гри одночасно слухати кілька незалежних каналів, не блокуючи роботу програми.

---

## 🧠 Що таке select: Аналогія з секретарем

Оператор `select` зовні дуже схожий на класичний `switch/case`, який ви використовуєте в PHP. Але якщо `switch` перевіряє значення однієї конкретної змінної, то `select` **перевіряє готовність каналів до введення або виведення даних**.

### Ідеальна аналогія:
Уявіть секретаря в офісі, у якого на столі стоїть два телефони:
- Телефон №1 — гаряча лінія від клієнтів (Канал подій від юнітів).
- Телефон №2 — внутрішній будильник, який дзвонить кожні 200 мс і нагадує, що треба зробити звіт (Канал тікера `ticker.C`).

Секретар не сидить, притиснувши до вуха лише одну слухавку. Він сидить і дивиться на обидва апарати. Щойно дзвонить телефон №2 — він миттєво малює кадр гри. Щойно дзвонить телефон №1 — він знімає слухавку, записує крок Орка чи Мага і знову повертається в режим очікування.

```go
select {
case event := <-world.MoveChannel:
    // Виконається МИТТЄВО, якщо юніт прислав свій хід
    world.ApplyMove(event)

case <-ticker.C:
    // Виконається МИТТЄВО, якщо підійшов час рендерингу кадру (200 мс)
    render.RenderWorld(world, turn, liveMages, liveOrcs)
}
```

## ⚙️ Зсув мислення: Асинхронний мультиплексинг сокетів у мові

Для PHP-розробників така поведінка коду є незвичною, оскільки в стандартному PHP-FPM ви не можете одночасно очікувати на події з різних джерел без сторонніх реактивних фреймворків (наприклад, `ReactPHP` або `Amphp`, які використовують системні виклики `select/poll/epoll`).

В Go цей складний механізм, який називається **мультиплексуванням каналів**, вбудований безпосередньо в синтаксис самої мови.

### 🚨 Важливе правило поведінки select:
1. **Випадковий вибір при одночасному спрацюванні:** Якщо в один і той самий наносекундний момент і таймер рендеру підійшов, і юніт прислав свій хід, Go обере один із кейсів **випадковим чином**. Це гарантує, що жоден канал не отримає постійного пріоритету і не заблокує інші (Starvation protection).
2. **Блок default для неблокуючого читання:** Якщо ви додасте блок `default`, оператор `select` взагалі перестане засинати. Він перевірить канали, і якщо вони порожні — миттєво виконає код у `default`.

## 🏗️ Обробка таймаутів: Механізм паніки на арені

Ще одна потужна фіча `select` — можливість створювати елегантні **таймаути** за допомогою функції `time.After()`. Це вкрай важливо для веб-розробки: якщо зовнішній API сервіс не відповідає більше ніж 2 секунди, ми не маємо права тримати з'єднання і навантажувати сервер, треба повернути помилку.

У нашій грі ми можемо впровадити захист від «зависання мозку» юнітів. Якщо гра не отримує взагалі жодної події від магів чи орків протягом, наприклад, 5 секунд, ми можемо констатувати, що горутини юнітів зависли або виник баг, і красиво завершити процес із повідомленням про помилку.

```go
select {
case event := <-world.MoveChannel:
    // Обробляємо хід юніта
case <-time.After(5 * time.Second):
    // Якщо за 5 секунд жоден інший кейс не спрацював, викликаємо таймаут
    fmt.Println("🚨 Помилка: Юніти заснули надовго! Завершення програми за таймаутом.")
    return
}
```

## 🎯 Що ми робимо на практиці в П'ятницю?

- Кожен розробник створює свою персональну гілку за шаблоном `feature/{name}-day-17` (або `day-5-week-3` залежно від вашого внутрішнього Git-нотатка);
- Модифікуємо головний ігровий цикл у `cmd/arena/main.go`;
- Обертаємо ігровий процес у нескінченний цикл, всередині якого розгортаємо конструкцію `select`;
- Кейс №1 слухає канал подій від юнітів `world.MoveChannel` і накопичує їх у буфер;
- Кейс №2 слухає канал фонового таймера `ticker.C` і виконує рендеринг карти з оновленими координатами один раз на 200 мс;
- Додаємо захисний кейс таймауту на випадок, якщо битва раптово зупиниться і всі горутини завершать роботу завчасно.
