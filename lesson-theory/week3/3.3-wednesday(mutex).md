# 📔 Теоретична частина. Тиждень 3, День 3 (День 15): Захист спільного стану за допомогою sync.Mutex

У попередній день (Вівторок) ми зіштовхнулися з суворою реальністю багатопотокового програмування — станом гонки (Race Condition). Детектор гонок Go (`-race`) наочно показав нам, що коли десятки автономних горутин-юнітів намагаються одночасно перезаписувати свої координати та здоров'я в єдиному просторі пам'яті світу `World`, програма стає нестабільною.

Сьогодні ми навчимося захищати наші дані. Ми розберемо найпопулярніший та фундаментальний інструмент синхронізації потоків — **Мутекс (`sync.Mutex`)**.

---

## 🧠 Що таке Mutex: Аналогія з туалетом у літаку

Назва `Mutex` походить від терміну **Mutual Exclusion** (взаємне виключення). Це найпростіший спосіб захисту спільного ресурсу: ми просто забороняємо горутинам чіпати дані одночасно.

### Ідеальна побутова аналогія:
Уявіть кабінку туалету в літаку. Це спільний ресурс для всіх пасажирів (горутин). 
- Коли пасажир заходить всередину, він закриває замок (**Lock**).
- Якщо у цей момент прибігають інші пасажири, вони не намагаються виламати двері. Вони слухняно встають у чергу і чекають.
- Коли перший пасажир виходить, він відкриває замок (**Unlock**). Тільки тепер наступна людина з черги може зайти всередину.

В Go мутекс працює точно так само на рівні оперативної пам'яті. Це електронний «замок», який ми вішаємо на нашу структуру.

```go
var mu sync.Mutex

mu.Lock()   // Горутина каже: "Я працюю з даними, всі інші — зачекайте!"
// ... тут безпечно змінюємо координати чи здоров'я юніта ...
mu.Unlock() // Горутина каже: "Я закінчила, наступна може заходити"
```

## 🏗️ Інтеграція Мутекса в Mage Arena

В PHP для вирішення подібних проблем на рівні бази даних ви використовували блокування рядків (`SELECT ... FOR UPDATE`) або атомарні замки в Redis (`$redis->set('lock', true, ['nx', 'ex' => 10])`). 

В Go ми робимо це безпосередньо всередині структури `World`, вбудовуючи туди `sync.Mutex` із стандартного пакету `"sync"`.

```go
type World struct {
    Width     int
    Height    int
    Units     []Unit
    BattleLog []string
    mu        sync.Mutex // Наш захисний замок для всього світу гри
}
```

### ⚠️ Головні правила роботи з мутексами для команди:

1. **Мутекс захищає не код, а пам'ять:** Сам по собі мутекс нічого не знає про ваші зрізи чи змінні. Він просто блокує виконання будь-якого іншого шматка коду, який теж намагається викликати `.Lock()` на цьому ж мутексі.
2. **Тримайте замок закритим мінімальний час:** Блок коду між `.Lock()` та `.Unlock()` називається *критичною секцією*. Намагайтеся триматися в ній якомога менше мілісекунд (тільки змінити координати чи записати лог). Якщо ви засунете всередину критичної секції важкі обчислення чи паузи (`time.Sleep`), ваша багатопотокова гра перетвориться на повільну однопотову чергу.
3. **Елегантне розблокування через `defer`:** Щоб випадково не забути викликати `.Unlock()` (наприклад, якщо всередині функції сталася помилка ходу і спрацював `return`), ідіоматично писати розблокування на наступному ж рядку через `defer`:
   ```go
   w.mu.Lock()
   defer w.mu.Unlock() // Замок гарантовано відкриється при виході з методу
   ```

## ⚙️ Зсув мислення: Від повної ізоляції до свідомого блокування

Для PHP-бекендерів робота з мутексами — це перехід на новий рівень відповідальності. В PHP-FPM рантайм сам ізолював розробника від паралельних потоків пам'яті. В Go ви стаєте повноцінними володарями заліза. Ви повинні чітко бачити, де горутини перетинаються, і явно розставляти «прапорці безпеки».

Якщо ви все зробите правильно, після додавання мутексів команда `go run -race` більше не видасть жодного попередження про конфлікти, а гра працюватиме стабільно ідіоматично.

## 🎯 Що ми робимо на практиці в Середу?

- Кожен розробник створює свою персональну гілку за шаблоном `feature/{name}-day-15` (або `day-3-week-3` залежно від вашого внутрішнього Git-нотатка);
- Додаємо поле `mu sync.Mutex` всередині структури `World` (`internal/models/world.go`);
- Захищаємо етап руху: метод `Move()` або логіку, де горутина-юніт намагається змінити свій стан всередині світу, обгортаємо у `w.mu.Lock()` та `w.mu.Unlock()`;
- Захищаємо етап боїв та логування подій у `main.go`, щоб читання та запис у `world.BattleLog` відбувалися потокобезпечно;
- Запускаємо гру знову через `go run -race cmd/arena/main.go` і переконуємося, що детектор гонок мовчить, а MVP працює бездоганно.
