# 📔 Теоретична частина. Тиждень 3, День 4 (День 16): Комунікація горутин за допомогою Каналів (Channels)

У попередній день (Середа) ми навчилися захищати спільну пам'ять за допомогою мутексів (`sync.Mutex`). Блокування — це надійний, перевірений часом інструмент, проте він має суттєвий мінус: велика кількість замків ускладнює код і може призвести до взаємного блокування потоків (**Deadlock**), коли програма зависає назавжди.

Сьогодні ми вивчимо візитну картку мови Go, яка кардинально відрізняє її від мов типу C++, Java чи PHP — **Канали (`channels`)**. Ми розберемо головну філософію Go: *«Не діліться пам'яттю за допомогою блокувань. Натомість діліться повідомленнями через канали»*.

---

## 🧠 Що таке Канал: Аналогія з конвеєром чи поштовою трубою

Канал (`chan`) — це вбудована у мову, абсолютно потокобезпечна черга (FIFO — First In, First Out). Ви можете уявити канал як пластикову пневматичну трубу на пошті або стрічку конвеєра.

- Одна горутина (наприклад, автономний мозок Орка) створює повідомлення про намір зробити крок і вкидає його в трубу.
- Інша горутина (наприклад, головний цикл гри `main`) сидить на іншому кінці труби, витягує звідти повідомлення і послідовно застосовує зміни до мапи.

### 🔀 Порівняння з PHP: Черги (RabbitMQ / Redis Queue) vs Канали
В PHP для асинхронної взаємодії процесів ви будували архітектуру черг: процес-продюсер кидає задачу в RabbitMQ або Redis (`redis-queue`), а фонові воркери (`php artisan queue:work`) її вигрібають. 

В Go цей складний інструмент побудований **безпосередньо на рівні мови і працює всередині оперативної пам'яті додатка**. Вам не потрібно піднімати зовнішній Redis для того, щоб передавати повідомлення між паралельними потоками.

## ⚙️ Синтаксис роботи з Каналами: Стрілочки `<-`

Канал створюється за допомогою вбудованої функції `make(chan ТипДаних)`. Для роботи з каналами використовується унікальний оператор-стрілочка **`<-`**, напрямок якої показує, куди рухаються дані.

```go
// 1. Створюємо канал, який вміє передавати тільки інтеджери
myChannel := make(chan int)

// 2. Запис у канал (стрілка вказує В КАНАЛ)
go func() {
    myChannel <- 42 // Горутина кинула число 42 в канал і заблокувалася, поки його хтось не зчитає
}()

// 3. Читання з каналу (стрілка вказує З КАНАЛУ в змінну)
value := <-myChannel
fmt.Println(value) // Виведе 42
```

### 🚨 Найважливіша властивість: Блокування (Blocking)
За замовчуванням канали є **небуферизованими**. Це означає, що коли горутина-відправник пише дані в канал (`ch <- data`), вона **зупиняється і чекає**, поки горутина-отримувач фізично не забере ці дані з іншого кінця (`<-ch`). Це забезпечує ідеальну синхронізацію: потокам не потрібні мутекси, канал сам контролює черговість дій.

## 🏗️ Нова архітектура Mage Arena: Перехід на Event-Driven модель

До сьогоднішнього дня наші юніти бігали в горутинах і самі міняли стан світу через мутекси. Сьогодні ми заберемо у юнітів право лізти в пам'ять карти. Ми перейдемо на **подієво-орієнтовану модель (Event-Driven Architecture)**.

Ми створимо структуру події ходу:
```go
type MoveEvent struct {
    UnitName string
    DX, DY   int
}
```

І додамо в наш `World` один глобальний канал подій:
```go
type World struct {
    // ... інші поля
    MoveChannel chan MoveEvent // Канал, куди юніти слатимуть свої ходи
}
```

### Як тепер працюватиме гра:
1. Мозок юніта (`Brain()`) прокидається в горутині, вираховує випадковий крок і замість виклику методу `Move()`, просто **кидає подію в канал**: `w.MoveChannel <- MoveEvent{UnitName: "Гендальф", DX: 1, DY: 0}`.
2. Головний цикл гри (`main.go`) більше не перебирає карту наосліп. Він у кожному кадрі тікера вичитує події з каналу. Оскільки читання з каналу відбувається в одному (головному) потоці, **нам більше не потрібні мутекси для захисту мапи** — всі зміни знову робить один єдиний потік, але дані до нього надходять із десятків паралельних горутин-юнітів!

## 🎯 Що ми робимо на практиці в Четвер?

- Кожен розробник створює свою персональну гілку за шаблоном `feature/{name}-day-16` (або `day-4-week-3` залежно від вашого внутрішнього Git-нотатка);
- Описуємо структуру події ходу `MoveEvent` в пакеті моделей;
- Ініціалізуємо канал подій через `make(chan MoveEvent)` всередині `World`;
- Переписуємо метод `Brain()` юнітів: тепер він приймає цей канал і відправляє туди повідомлення про намір зробити крок;
- У файлі `main.go` або методі `Tick()` ми реалізуємо зчитування подій з каналу, безпечно оновлюючи координати та прораховуючи колізії в одному потоці.
