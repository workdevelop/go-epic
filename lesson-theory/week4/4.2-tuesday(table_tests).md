## 🧠 Рідне тестування в Go: Жодних external залежностей

У світі Go розробникам не потрібно встановлювати сторонні пакети через `go get`, щоб почати писати тести. Усе вбудовано безпосередньо в компілятор мови на рівні стандартного пакету `"testing"` та системної команди `go test`.

### Три золоті правила файлів тестування в Go:
1. **Іменування файлів:** Файл із тестами обов'язково повинен мати суфікс `_test.go` і лежати в тій самій папці (пакеті), що й код, який він тестує. Наприклад, тести для `mage.go` мають лежати у файлі `mage_test.go`.
2. **Іменування функцій:** Кожна функція тесту повинна починатися з великого слова `Test` та приймати один єдиний аргумент — вказівник на об'єкт тестування `t *testing.T`.
   ```go
   func TestMageMovement(t *testing.T) { ... }
   ```
3. **No Assertions Magic:** В Go немає магічних функцій типу `$this->assertEquals()` чи `$this->assertTrue()`. Перевірка результату робиться через звичайнісінькі оператори порівняння `if`. Якщо результат не збігається з очікуваним, ми сигналізуємо про це через метод `t.Errorf()`.

## ⚙️ Паттерн дня: Табличні тести (Table-Driven Tests)

В PHP, якщо вам потрібно протестувати метод з різними вхідними даними, ви використовуєте анотації або атрибути дата-провайдерів:
```php
/** @dataProvider movementProvider */
public function testMove(\$dx, \(dy,\)expectedX) { ... }
```

В Go замість дата-провайдерів використовується набагато більш явний і красивий підхід — **Табличні тести (Table-Driven Tests)**. Це золотий стандарт спільноти Golang.

Ми описуємо анонімну структуру, яка представляє собою "рядок таблиці" з вхідними даними та очікуваним результатом. Потім ми створюємо масив (зріз) таких рядків і проганяємо їх в одному єдиному циклі.

```go
func TestMage_Move(t *testing.T) {
    // 1. Визначаємо тестову таблицю (масив кейсів)
    tests := []struct {
        name        string
        dx, dy      int
        expectError bool
    }{
        {"Успішний крок вперед", 1, 0, false},
        {"Врізання в ліву стіну", -5, 0, true},
        {"Врізання в верхню стіну", 0, -5, true},
    }

    // 2. Ітеруємося по таблиці
    for _, tt := range tests {
        // Запускаємо ізольований під-тест через t.Run
        t.Run(tt.name, func(t *testing.T) {
            mage := Mage{Position: Position{X: 2, Y: 2}}
            err := mage.Move(tt.dx, tt.dy, 12, 12)

            if (err != nil) != tt.expectError {
                t.Errorf("Move() помилка = %v, очікували помилку: %v", err, tt.expectError)
            }
        })
    }
}
```

## 🏗️ Що саме ми покриваємо тестами у Mage Arena

Сьогодні ми сфокусуємося на ізольованому тестуванні чистої бізнес-логіки моделей, яка не залежить від багатопотоковості. Ми напишемо табличні тести для трьох критичних зон:

1. **Валідація меж карти (`Move`):** Перевіряємо, що коли юніт намагається зробити легальний крок, метод повертає `nil` і координати змінюються. Якщо крок веде в стіну (`X <= 0` чи `Y <= 0`) — метод залізно повертає об'єкт помилки, а юніт залишається на місці.
2. **Механіка отримання урону (`TakeDamage`):** Перевіряємо, що здоров'я зменшується коректно. Окремий тест-кейс має підтвердити "захист від від'ємного HP": якщо у мага було 10 HP, а орк вдарив на 50, здоров'я має стати рівно `0`, а не `-40`.
3. **Движок бою (`engine.Battle`):** Перевіряємо, що функція сутички коректно розраховує зменшення здоров'я обох опонентів на величину нанесені шкоди.

## 🎯 Що ми робимо на практиці у Вівторок?

- Кожен розробник створює свою персональну гілку за шаблоном `feature/{name}-day-20` (або `day-2-week-4` залежно від вашого внутрішнього Git-нотатка);
- У папці `internal/models/` створюємо файли `mage_test.go` та `orc_test.go`;
- У папці `internal/engine/` створюємо файл `combat_test.go`;
- Наповнюємо їх табличними тестами для перевірки мутації стану (рух, урон, бойова сутичка);
- Запускаємо тести в терміналі VS Code за допомогою швидкої та потужної команди:
  ```bash
  go test ./... -v
  ```
  Прапорець `./...` каже Go рекурсивно знайти всі тести в усіх пакетах проєкту, а `-v` (verbose) виведе красивий текстовий звіт із назвою кожного успішного під-тесту.
