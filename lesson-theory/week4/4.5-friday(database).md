## 🧠 PDO в PHP vs database/sql в Go: Головні відмінності

Для PHP-розробників, які звикли взаємодіяти з базами даних через абстракцію **PDO** або важкі ORM (на кшталт `Eloquent` в Laravel чи `Doctrine` в Symfony), підхід Go може здатися занадто низькорівневим, але він забезпечує максимальну прозорість та швидкість обробки даних.

### Як це працює в Go (Пакет `database/sql`):
1. **Інтерфейс стандартної бібліотеки:** В Go є вбудований пакет `"database/sql"`. Він не вміє сам підключатися до жодної конкретної бази даних. Він описує лише загальні інтерфейси (`DB`, `Rows`, `Stmt`).
2. **Драйвери баз даних (Drivers):** Щоб підключитися до SQLite, PostgreSQL чи MySQL, ви завантажуєте легковажний сторонній драйвер. Цей драйвер неявно реєструє себе всередині пакета `database/sql`. Весь ваш подальший код пишеться суто за стандартами Go, без прив'язки до специфіки конкретної БД.
3. **Пул з'єднань «з коробки» (Connection Pooling):** В PHP-FPM кожен окремий процес створює одне з'єднання з MySQL, виконує запит і закриває його (або використовує `pconnect`). В Go об'єкт `*sql.DB` — це **автоматичний, вбудований пул з'єднань**. Він тримає відкритими, наприклад, 10 конектів і самостійно розподіляє їх між тисячами паралельних горутин-HTTP-запитів клієнтів.

## ⚙️ Робота з рядками та сканування даних (Data Scanning)

Оскільки Go — статично типізована мова, вона не може просто повернути вам рядок з бази у вигляді динамічного масиву, як це робить PHP (`$row = $stmt->fetch(PDO::FETCH_ASSOC)`). 

В Go ви повинні явно підготувати змінні потрібних типів і скористатися методом **`.Scan()`**, який розкладе колонки з SQL-відповіді по комірках пам'яті ваших змінних.

```go
// Приклад зчитування даних у Go
var id int
var name string
var health int

// Виконуємо запит до БД
err := db.QueryRow("SELECT id, name, health FROM match_stats WHERE id = ?", 1).Scan(&id, &name, &health)
if err != nil {
    log.Fatal(err)
}
```
* **Зверніть увагу:** Ми передаємо у метод `.Scan()` саме **вказівники** (`&id`, `&name`), щоб функція могла записати отримані з бази дані безпосередньо в наші локальні змінні.

## 🏗️ Архітектура збереження матчів у Mage Arena

Сьогодні ми створимо таблицю `match_history`, яка фіксуватиме фінал кожної битви на арені:
```sql
CREATE TABLE IF NOT EXISTS match_history (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    played_at DATETIME,
    winner TEXT,
    turns_total INTEGER
);
```

Коли гра добігає кінця (наприклад, масиви юнітів спорожніли, і в `main.go` спрацьовує умова перемоги магів або орків), наш додаток не просто виведе повідомлення у консоль. 

Перед завершенням або перезапуском процесу головний потік виконає SQL-запит `INSERT INTO match_history ...`, зафіксувавши:
- Точний час завершення матчу (`time.Now()`),
- Назву раси, яка перемогла (`Маги` або `Орки`),
- Загальну кількість кадрів (ходів), які тривала ця епічна битва.

Ми також додамо новий HTTP-ендпоінт `/history`, який зчитуватиме ці дані з бази через `SELECT` та віддаватиме користувачу гарну історію всіх попередніх запусків симулятора.

## 🎯 Що ми робимо на практиці в П'ятницю?

- Кожен розробник створює свою персональну гілку за шаблоном `feature/{name}-day-23` (або `day-5-week-4` залежно від вашого внутрішнього Git-нотатка);
- Завантажуємо драйвер для бази даних (наприклад, сучасний чистий драйвер для SQLite: `go get ://github.com` або стандартний `modernc.org/sqlite`);
- У функції `main()` ініціалізуємо підключення до файлу бази даних через `sql.Open("sqlite3", "arena.db")`;
- Обов'язково реєструємо `defer db.Close()`, щоб база коректно закривала дескриптори файлів при вимкненні сервера;
- Пишемо SQL-запит для створення таблиці автоматично при старті програми (Migration);
- Реалізуємо логіку збереження фінальної статистики матчу після виходу з ігрового циклу;
- Створюємо новий HTTP-хендлер `/history`, який повертає JSON-список усіх зіграних матчів.
