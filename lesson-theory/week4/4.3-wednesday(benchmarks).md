## 🧠 Бенчмарки в Go: Аналог у PHP та рідний інструментарій

У світі PHP вимірювання продуктивності зазвичай вимагає встановлення важких зовнішніх розширень для профілювання (на кшталт `Xdebug`, `Blackfire.io` чи `tideways`). Для простих замірів розробники часто пишуть ручний код із `microtime(true)`.

В Go інструментарій для мікро-оптимізацій та бенчмаркінгу є **частиною самої мови**. Він вбудований у той самий стандартний пакет `"testing"`, який ми розбирали вчора.

### Три правила написання бенчмарку в Go:
1. **Іменування функцій:** Функція бенчмарку повинна починатися з великого слова `Benchmark` і лежати у файлі з суфіксом `_test.go`.
2. **Аргумент тесту:** Вона приймає вказівник на об'єкт тестування швидкодії `b *testing.T`.
3. **Цикл навантаження:** Всередині функції обов'язково має бути цикл, який повторює цільовий алгоритм `b.N` разів. Кількість ітерацій `b.N` визначає сам рантайм Go, постійно збільшуючи її, поки не отримає статистично точний результат.

```go
func BenchmarkSearchEnemy(b *testing.T) {
    world := prepareLargeWorld() // Підготовка даних (не враховується в замір)
    b.ResetTimer()              // Скидаємо таймер, щоб не враховувати час підготовки

    for i := 0; i < b.N; i++ {
        world.FindClosestEnemy(world.Units[0]) // Алгоритм, який ми тестуємо
    }
}
```

## ⚙️ Що ми вимірюємо: Швидкість та Алокації (Heap Allocations)

Коли ви запускаєте бенчмарк у Go, утиліта повертає три ключові метрики:
1. **`ns/op` (Наносекунди за операцію):** Скільки часу зайняв один виклик функції. 1 наносекунда = 0.000000001 секунди.
2. **`B/op` (Байти за операцію):** Скільки оперативної пам'яті виділила функція в купі (Heap) за один виклик.
3. **`allocs/op` (Алокації за операцію):** Скільки разів рантайм Go просив операційну систему виділити новий шматок пам'яті.

### 🔀 Зсув мислення: Чому алокації — це ворог високого навантаження?
В PHP-FPM пам'ять виділяється хаотично під мільйони динамічних масивів та об'єктів, а після завершення запиту все разом стирається. Нам байдуже, скільки разів PHP виділяв пам'ять під час виконання скрипта.

В Go додаток працює безперервно. Кожна алокація в купу (`Heap`) означає, що цей об'єкт пізніше доведеться видаляти **Збирачу Сміття (Garbage Collector)**. Якщо високочастотний алгоритм (як-от пошук ворога 5 кадрами на секунду для 1000 юнітів) робить хоча б 1 алокацію на крок, Garbage Collector почне постійно вмикатися, навантажуючи процесор сервера на 30–40% суто на очищення пам'яті. 

> **Золотий стандарт Go-оптимізації:** Досягти `0 allocs/op` у критичних для продуктивності алгоритмах. Це означає, що весь код працює на надшвидкому стеку (Stack Memory) і взагалі не чіпає повільну купу та Garbage Collector.

## 🏗️ Оптимізація алгоритму пошуку найближчого ворога

Сьогодні ми додамо в наш `World` новий тактичний метод — `FindClosestEnemy(u Unit) Unit`. Кожен юніт у майбутньому буде використовувати його, щоб бігти не хаотично, а цілеспрямовано атакувати найближчого супротивника іншої раси.

### Етапи практичного заняття:
1. **Наївна реалізація (Брутфорс):** Ми напишемо простий пошук через математичну формулу відстані між точками Pythagoras. Всередині циклу ми будемо динамічно створювати нові структури для підрахунку результату.
2. **Запуск бенчмарку:** Ми побачимо, що алгоритм займає багато наносекунд та робить алокації пам'яті.
3. **Оптимізація (Zero Allocation):** Ми перепишемо алгоритм так, щоб він перевикористовував пам'ять, передавав структури виключно за значенням (без вказівників, де це можливо), уникаючи втечі об'єктів у купу (Escape Analysis).

- Кожен розробник створює свою персональну гілку за шаблоном `feature/{name}-day-21` (або `day-3-week-4` залежно від вашого внутрішнього Git-нотатка);
- У файлі `internal/models/world.go` реалізуємо метод пошуку найближчого живого ворога іншої раси;
- Створюємо новий файл тесту продуктивності `internal/models/world_bench_test.go` та пишемо туди функцію `BenchmarkFindClosestEnemy`;
- Запускаємо бенчмарк за допомогою спеціального прапорця в терміналі:
  ```bash
  go test ./internal/models -bench=. -benchmem
  ```
  Прапорець `-bench=.` каже Go запустити всі бенчмарки у цьому пакеті, а `-benchmem` виведе детальну статистику про виділення байтів та кількість алокацій;
- Оптимізуємо алгоритм і переконуємося, що швидкість зросла, а метрика `allocs/op` впала до омріяного нуля `0`.
